## 2. 프로젝트 개요

이 프로젝트는 사회 초년생 페르소나의 모의 계좌 거래 내역을 분석해 소비 패턴, 반복 지출 후보, 절약 전략을 보여주는 서비스의 장애 대응 흐름을 정의한다. 거래 내역은 프로젝트에서 제공하는 모의 API로 공급한다. 서비스는 근거를 제시하며 추천까지만 하고, 결제 취소·변경 등 실제 금융 행동은 사용자에게 맡긴다.

분석은 통계와 규칙을 바탕으로 한다. 월별 구독·식비 합계와 적금액의 관계를 관찰해 제시하되, 상관관계를 원인이나 확정적 절약 효과로 표현하지 않는다. Auto Healing은 모의 API의 오류·지연·연결 실패를 탐지하고 제한적으로 재시도한 뒤 결과를 독립 검증하거나 사람에게 전달한다.

Python과 FastAPI로 분석 API 및 모의 거래 API를 구성한다. Day 2에는 개인 노트북의 Docker Compose로 개발·검증하고, Day 3에는 같은 두 컨테이너를 단일 AWS EC2 테스트 인스턴스에 배포한다. 개발팀은 4명이다. 데이터베이스, 도메인, 자동 배포 파이프라인은 사용하지 않는다.

## 3. 문제 정의

수입이 넉넉하지 않은 사회 초년생은 월세, 통신비, 식비, 적금과 여러 정기 구독 등으로 지출을 관리해야 한다. 소비 내역을 직접 살펴 고정 지출과 절약 가능성을 찾는 데 시간이 들고, 모의 거래 데이터 제공 API가 실패하면 분석 결과를 받을 수 없다.

본 MVP는 모의 계좌 데이터를 읽어 지출 패턴과 반복 지출 후보를 찾아 근거가 있는 추천을 제공하고, 데이터 API 장애를 안전하게 처리하는 방법을 보여준다. 외부 API 장애가 발생해도 잘못되거나 불완전한 분석 결과를 정상 결과처럼 보여주지 않는 것이 핵심이다.

## 4. 사용자와 이해관계자

### 주요 사용자 페르소나

- 수입이 넉넉하지 않은 사회 초년생
- 넷플릭스, 유튜브 프리미엄 등 복수의 정기 구독이 있음
- 식비, 월세, 통신비, 적금 등 반복 지출이 있음
- 구체적인 월수입과 거래 금액은 실제 개인 자료가 아니라 모의 값으로 설정함

### 데모용 모의 프로필

아래 금액은 모두 교육용 모의 값이며 실제 개인이나 시장 가격을 나타내지 않는다.

- 월 실수령액: 2,400,000원(교육용 모의 값)
- 월세: 650,000원, 통신비: 55,000원, 구독 합계: 약 35,000원(모의 값)
- 식비: 월 450,000~650,000원 범위에서 변동
- 교통비: 월 약 80,000원
- 기타 재량 지출: 월 150,000~350,000원 범위에서 변동
- 적금 납입: 월 150,000~350,000원 범위에서 변동
- 12개월 전체를 모의 값으로 구성하고 실제 서비스 가격·생활비 통계로 해석하지 않는다.

### 이해관계자

- 사용자: 분석 결과와 근거를 검토하고 추천의 실제 적용 여부를 결정
- 개발팀 4명: 백엔드 구현, 로컬 검증, AWS 테스트 배포
- 교육 검토자: PRD 범위와 승인 여부 확인 [검토자 미결정]
- AWS 샌드박스 담당자: EC2 생성 권한과 팀 IP 접근 허용 제공. Day 1에 접근 가능 여부 확인

## 5. 목표와 성공 기준

### 목표

1. 12개월치 모의 거래 내역을 이용해 수입, 구독, 식비, 월세, 통신비, 교통비, 기타 변동 지출, 적금 내역을 분석한다.
2. 반복 지출 후보와 절약 전략에 기간·범주·금액 등 확인 가능한 근거를 붙인다.
3. 월별 구독·식비 합계와 적금액 간 관찰된 상관 패턴을 제시한다.
4. 모의 거래 API의 HTTP 5xx, 지연·타임아웃, 연결 실패를 안전하게 재현하고 대응 결과를 추적한다.
5. 복구 동작과 별도의 검증 단계가 API와 핵심 분석 결과를 확인한다.
6. 백엔드와 모의 API를 한 EC2 테스트 인스턴스에 배포해 팀이 핵심 API를 확인할 수 있다.

### 성공 기준

- 분석 응답에 12개월 데이터의 분석 기간과 사용된 범주·금액 근거가 나타나며, 반복 구독 후보는 월·연 지출 규모를 보여준다.
- 상관 분석 결과는 Pearson 상관계수와 관찰 기간·사용한 월별 데이터 수를 표시하고, 인과관계로 표현하지 않는다.
- HTTP 5xx, 타임아웃, 연결 실패를 한 번씩 주입하는 세 번의 데모 실행에서 탐지·시도·검증 결과가 사건 기록으로 남는다.
- 장애당 최초 요청 이후 재시도는 최대 2회이며, 계속 실패하면 중단하고 알림을 보낸다.
- 정상 기준 요청은 사건을 만들지 않고, 세 번의 장애 주입 실행은 모두 사건으로 기록한다(장애 탐지 3/3, 정상 기준 오탐 0/1).
- 일시적 HTTP 5xx와 타임아웃은 재시도 후 독립 검증을 통과하고, 지속 연결 실패는 상한 도달 후 차단·알림한다.
- 전체 요청 흐름은 20초 안에 정상 결과 또는 실패 알림으로 종료한다.
- EC2 배포본의 헬스체크와 정상 분석 요청이 성공하고, 백엔드 접근은 팀 IP로 제한되며 모의 API는 컨테이너 내부에서만 접근 가능하다.
- 모의 API가 정상 응답한 것만으로 분석 복구 완료를 선언하지 않고, 독립 검증이 데이터 완전성과 핵심 분석 응답을 확인한다.
- 상관계수는 Pearson 방식으로 계산한다. 장애 감지시간과 정상화시간을 기록하고, MTTD 3초 이내·전체 정상화 또는 실패 판정 20초 이내를 목표로 한다.

## 7. 정상 서비스 시나리오

1. 사용자가 소비 분석을 요청한다.
2. 서비스가 모의 거래 내역 API에서 페르소나의 12개월치 모의 거래를 조회한다.
3. 데이터의 기간과 필수 항목을 확인한다.
4. 소비 범주별 지출과 반복 구독 후보를 분석한다.
5. 월별 구독·식비 합계와 적금액의 상관 패턴을 분석한다.
6. 결과·근거·관찰의 한계를 포함해 절약 전략 후보를 제시한다.
7. 사용자가 추천을 검토하고 실제 적용 여부를 직접 결정한다.

불완전한 데이터, API 실패 또는 분석 검증 실패가 발생하면 불완전한 추천을 확정 결과로 표시하지 않고 오류 상태와 확인 가능한 원인을 보여준다.

## 8. 장애 시나리오

| 장애 | 발생 위치 | 탐지 신호 | 사용자·운영 영향 | 안전한 재현 방법 | 예상 복구 방향 |
|---|---|---|---|---|---|
| HTTP 5xx | 모의 거래 내역 API | HTTP 오류 상태 | 분석 요청 실패 또는 지연 | 모의 API가 지정된 요청에 오류 응답 | 최대 2회 재시도 후 중단·알림 |
| 응답 지연·타임아웃 | 모의 거래 내역 API | 정해진 응답 제한시간 초과 | 결과가 늦거나 분석 불가 | 모의 API 응답 지연 | 제한적 재시도 후 독립 확인 또는 알림 |
| 연결 실패 | 모의 거래 내역 API | 연결 오류·헬스체크 실패 | 거래 데이터 조회 불가 | 테스트용 모의 API를 일시적으로 이용 불가 상태로 설정 | 제한적 재시도, 반복 실패 시 회로 차단·알림 |

데모에서는 세 가지 장애 유형을 한 번씩 실행한다. HTTP 5xx와 타임아웃은 재시도 후 회복하고, 지속 연결 실패는 재시도 상한에 도달해 회로를 연다.

실제 계좌나 운영 서비스에는 장애를 주입하지 않는다. API 요청 제한시간은 3초다. 연결 오류가 한 사건에서 총 3회(최초 요청 1회와 재시도 2회) 발생하면 회로를 열고 자동 호출을 중지한다. 사람이 API 헬스체크 정상 확인 후 명시적으로 재개해야 한다. 장애 주입은 로컬 또는 팀 IP로 제한된 EC2 데모 환경에서만 수행한다.

## 9. 멀티 에이전트 구성

역할을 분리해 책임과 권한을 명확히 한다. MVP에서는 통계 계산과 역할 간 협업을 별도 LLM 에이전트가 아니라 결정적 로직과 상태 흐름으로 구성한다.

### Monitor

- 책임: 모의 거래 API 상태와 응답 신호를 관찰하고 사건 생성
- 입력: 헬스체크, HTTP 상태, 응답시간, 요청 식별자
- 출력: 장애 이벤트와 증거
- 사용할 수 있는 정보: 모의 API의 비민감 상태 정보
- 허용 행동: 조회, 사건 기록
- 금지 행동: 복구 직접 실행, 분석 정책 변경
- 실패 시 행동: 관찰 불가 증거를 기록하고 오케스트레이터에 전달

### Diagnosis

- 책임: 증거를 기준으로 HTTP 오류, 타임아웃, 연결 실패 등을 분류
- 입력: 장애 이벤트, 응답 상태, 시간, 재시도 이력
- 출력: 분류, 근거, 허용된 복구 제안
- 사용할 수 있는 정보: 모의 API 응답과 사건 이력
- 허용 행동: 증거 조회와 제안
- 금지 행동: 복구 직접 실행, 증거 없는 원인 단정
- 실패 시 행동: 원인 불명으로 분류하고 자동 복구 중단을 제안

### Recovery

- 책임: 승인된 정책 안에서 제한된 재시도 수행
- 입력: 분류 결과와 사건 상태
- 출력: 시도 횟수와 수행 결과
- 사용할 수 있는 정보: 사건별 정책과 API 상태
- 허용 행동: 읽기 전용 조회의 최대 2회 재시도
- 금지 행동: 거래 데이터 변경·삭제, 실제 금융 행동, 임의 명령 실행
- 실패 시 행동: 추가 시도를 멈추고 오케스트레이터에 보고

### Verification

- 책임: 복구 후 API와 분석 결과를 독립 확인
- 입력: 조회 결과, 분석 응답, 복구 기록
- 출력: 통과·실패 및 확인 근거
- 사용할 수 있는 정보: 모의 거래 데이터와 비민감 결과
- 허용 행동: 헬스체크, 필수 데이터·분석 결과 확인
- 금지 행동: 복구 실행, 자기보고만으로 성공 처리
- 실패 시 행동: 사건을 미해결로 표시하고 알림

### Orchestrator

- 책임: 상태, 역할 순서, 타임아웃, 총 재시도 상한, 중단·에스컬레이션 관리
- 입력: 역할별 결과와 사건 이력
- 출력: 다음 역할 호출, 완료 또는 중단 결정
- 사용할 수 있는 정보: 사건 식별자와 비민감 상태 정보
- 허용 행동: 역할 호출과 정책상 상태 전이
- 금지 행동: 정책 우회, 거래 데이터 조작, 직접 금융 행동
- 실패 시 행동: 안전하게 중단하고 사건을 미해결로 기록

### Notification

- 책임: 사용자 또는 담당자에게 실패·검증 결과 전달
- 입력: 최종 사건 상태와 근거
- 출력: 상태 알림
- 허용 행동: 결과와 다음 확인사항 전달
- 금지 행동: 자동 복구 정책 변경, 결과를 과장
- 실패 시 행동: 전달 실패를 기록

역할 간 처리는 별도 LLM 에이전트 없이 결정적 로직과 상태 흐름으로 구성한다. 실패 알림은 분석 API 응답과 컨테이너 실행 로그로 전달하며 외부 메시징 서비스는 연결하지 않는다.

## 10. 에이전트 협업 흐름

```text
요청·모의 API 상태 관찰
→ Monitor가 증거와 사건 ID 기록
→ Orchestrator가 제한·순서 확인
→ Diagnosis가 장애 유형과 근거 분류
→ Recovery가 읽기 전용 재시도를 최대 2회 수행
→ Verification이 API와 핵심 분석 결과를 독립 확인
→ 통과 시 정상 결과 전달
→ 실패·원인 불명·상한 도달 시 중단하고 Notification으로 알림
```

분석·통계 계산은 동일한 모의 입력에 대해 재현 가능한 결과를 내야 한다. 역할 간 전달 정보는 사건 ID, 추적 ID, 장애 유형, 증거, 시각, 시도 횟수, 제안 행동, 검증 상태로 통일한다. 전체 흐름 제한시간은 20초다.

## 12. 자율성과 Human-in-the-loop

### 자동 실행 가능

- 모의 API 헬스체크와 읽기 전용 조회
- 장애별 최대 2회 재시도
- 사건 기록, 검증, 실패 알림

### 사람 승인 후 실행

- 회로가 열린 뒤에는 사람이 모의 API 헬스체크 정상 응답을 확인하고 명시적으로 재개해야 한다.
- 서비스가 추천한 절약 전략의 실제 적용은 사용자 판단으로 한다.

### 자동 실행 금지

- 실제 결제·이체·정기 결제 취소·투자 주문
- 실제 계좌나 개인정보 접근
- 모의 거래 데이터 임의 변경·삭제
- 허용목록 밖의 서비스 조작, 임의 명령 실행
- 독립 검증 없이 성공 선언

## 13. 기능 요구사항

### FR-001 모의 거래 내역 제공

- 설명: 서비스는 페르소나의 모의 계좌에서 12개월치 모의 거래 데이터를 모의 API로 조회해야 한다.
- 입력: 분석 요청과 페르소나 식별자
- 기대 동작: 수입, 구독, 식비, 월세, 통신비, 교통비, 기타 변동 지출, 적금 범주에 해당하는 자료를 제공한다.
- 예외 상황: API 오류·지연·연결 실패·필수 데이터 누락 시 정상 분석처럼 처리하지 않는다.
- 인수조건: 요청에 사용된 기간과 조회 실패 상태를 추적할 수 있다.

### FR-002 거래 데이터 유효성 확인

- 설명: 분석 전에 기간, 필수 범주, 금액 필드의 유효성을 확인한다.
- 입력: 모의 API 응답
- 기대 동작: 유효 데이터만 분석 단계로 전달하고 누락·잘못된 응답을 식별한다.
- 예외 상황: 유효성 확인 실패 시 추천을 생성하지 않고 근거와 함께 실패 상태를 반환한다.
- 인수조건: 누락 또는 잘못된 데이터가 정상 결과로 표시되지 않는다.

### FR-003 소비 패턴 및 반복 구독 후보 분석

- 설명: 범주별 금액과 반복성을 분석한다.
- 입력: 유효한 12개월 거래 내역
- 기대 동작: 구독·식비·월세·통신비·교통비·기타 변동 지출 등 범주별 합계와 반복 구독 후보를 제시한다.
- 예외 상황: 반복 기준이 모호하거나 데이터가 부족한 후보는 확정 항목이 아닌 후보로 표시한다.
- 인수조건: 반복 구독은 최근 4개월 중 3개월 이상 같은 가맹점에서 발생하고 각 금액이 해당 기간 중앙값의 ±10% 이내일 때 후보로 표시한다. 모든 후보에 기간·거래·금액 근거가 표시된다.

### FR-004 상관 패턴 제시

- 설명: 월별 구독·식비 합계와 적금액 사이의 상관 패턴을 분석한다.
- 입력: 12개월의 월별 집계 데이터
- 기대 동작: Pearson 상관계수, 관계 방향, 사용한 기간·월 수와 월별 수치 근거를 제시한다.
- 예외 상황: 유효한 월별 쌍이 12개가 아니거나 두 값 중 하나의 월별 변동이 없으면 계수를 표시하지 않고 이유를 알린다.
- 인수조건: 12개월의 월별 구독+식비 합계와 적금액으로 Pearson r을 계산하고 소수 둘째 자리, 기간, 표본 월 수(n=12)를 표시한다. 인과관계·통계적 유의성·보장된 절약 효과를 주장하지 않는다.

### FR-005 절약 전략 추천

- 설명: 소비 분석 결과와 상관 패턴을 참고해 사용자가 검토할 절약 전략을 제시한다. 상관계수만으로 전략을 추천하지 않는다.
- 입력: 소비 범주, 반복 지출 후보, 분석 근거
- 기대 동작: 범주별 소비 비교와 반복 구독 검토 등 사용자가 고려할 행동과 추천 근거를 설명한다. 가장 최근 달 식비가 직전 11개월 중앙값보다 20% 이상 높으면 식비 검토를 제안한다. 반복 구독은 월 금액과 연간 환산 지출 규모를 보여주며, 사용자가 직접 조정·취소를 결정할 경우의 절감 가능액은 추정치로 표시한다.
- 예외 상황: 근거 데이터가 부족하면 추천을 보류하거나 한계를 표시한다.
- 인수조건: 추천마다 연결된 범주·기간·금액 근거가 있고 실제 금융 행동을 실행하지 않는다. 절감 가능액은 가정에 따른 추정치로 명시한다. 상관관계를 인과관계로 해석하지 않으며, 기준을 넘는 소비 패턴이 없으면 절약 추천을 억지로 생성하지 않는다.

### FR-006 장애 이벤트 생성

- 설명: 거래 API 실패를 사건으로 기록한다.
- 입력: HTTP 오류, 타임아웃, 연결 실패 등 관찰 신호
- 기대 동작: 사건 ID, 발생 시각, 신호, 추적 ID를 남긴다.
- 예외 상황: 원인 분류가 불가능하면 미분류 상태로 사람에게 전달한다.
- 인수조건: 세 가지 장애 유형의 발생·탐지 정보가 구분되어 기록된다.

### FR-007 제한적 복구

- 설명: 허용된 정책에 따라 읽기 전용 API 호출을 제한적으로 재시도한다.
- 입력: 사건과 분류 결과
- 기대 동작: 최초 요청 뒤 최대 2회 재시도하고 한도 이후 중단·알림한다.
- 재시도 대기는 1초와 2초, API 요청 제한시간은 3초, 전체 흐름 제한시간은 20초다.
- 예외 상황: 반복 실패 시 회로 차단 상태로 전환한다.
- 인수조건: 모든 시도와 중단 사유가 사건 ID에 연결된다.

### FR-008 독립 복구 검증

- 설명: 복구 수행 결과와 독립적으로 API 및 분석 응답을 검증한다.
- 입력: API 상태, 거래 데이터, 분석 응답
- 기대 동작: 필수 기간·데이터·핵심 결과가 정상인지 판정한다.
- 예외 상황: 확인 실패 시 사건을 미해결로 남기고 알림한다.
- 인수조건: Recovery 성공 보고만으로 완료되지 않는다.

### FR-009 사건 추적 및 알림

- 설명: 장애부터 최종 검증까지 이력을 보존하고 실패 시 알린다.
- 입력: 사건 단계별 이벤트
- 기대 동작: 사건·추적 ID, 시간, 증거, 시도, 검증 결과를 연계한다.
- 예외 상황: 알림 실패도 기록한다.
- 인수조건: 각 장애 시나리오의 전 과정을 로그에서 확인할 수 있다.

### FR-010 배포 상태 확인

- 설명: 배포된 분석 API의 상태와 핵심 기능을 확인할 수 있어야 한다.
- 입력: 팀이 호출하는 헬스체크 또는 정상 분석 요청
- 기대 동작: API 상태를 반환하고 정상 요청에서 분석 결과를 제공한다.
- 예외 상황: API 비정상 또는 모의 거래 API 연결 실패 시 실패 상태를 반환하고 로그를 남긴다.
- 인수조건: EC2 배포본에서 헬스체크와 한 건의 정상 분석 요청이 성공하며, 모의 거래 API 포트는 컨테이너 네트워크 밖에서 접근할 수 없다.

## 14. 비기능 요구사항

### NFR-001 안전성

- 실습은 모의 데이터와 모의 API에만 수행한다.
- 재시도는 최초 요청 이후 최대 2회로 제한한다.
- 회로 차단·타임아웃·실패 알림으로 무한 복구를 방지한다.
- 독립 검증 전에는 정상 복구를 선언하지 않는다.

### NFR-002 개인정보 보호

- 실제 계좌·개인정보·인증정보를 사용하거나 기록하지 않는다.
- 로그에는 모의 데이터만 포함한다.

### NFR-003 재현성

- 모의 입력과 장애 유형을 반복 재현할 수 있어야 한다.
- 동일 입력에 대한 통계·규칙 계산은 재현 가능해야 한다.

### NFR-004 관측 가능성

- 사건 ID와 단계별 시각·증거·결과를 기록한다.
- 탐지시간과 정상화 시간을 계산할 수 있도록 시각을 보존한다.

### NFR-005 설명 가능성

- 소비 분석과 추천은 기간·범주·금액 등 근거를 포함한다.
- 상관 패턴은 한계와 함께 제시하고 인과 표현을 피한다.

### NFR-006 성능

- 모의 거래 API 요청 제한시간은 3초다. 전체 요청 흐름은 정상 결과 또는 실패 알림을 20초 안에 반환해야 한다.

### NFR-007 AWS 데모 배포

- 분석 API와 모의 거래 API를 한 AWS EC2 테스트 인스턴스의 Docker Compose에서 실행한다.
- 분석 API 인바운드는 팀의 지정 IP에서만 허용하고, 모의 거래 API는 내부 컨테이너 네트워크에만 노출한다.
- AWS 자격 증명·SSH 키를 저장소에 넣지 않는다. 실제 계좌·개인정보는 전송하지 않는다.
- 도메인·TLS, 인증, 고가용성, 오토스케일링, 외부 로그·모니터링 서비스는 이 3일 데모에 포함하지 않는다.
- 데모와 검토가 끝난 뒤 EC2 인스턴스를 종료·삭제해 지속 실행 비용을 방지한다.

## 15. 데이터와 로그 요구사항

### 모의 거래 데이터

최소 논리 항목: 모의 거래 식별자, 날짜·월, 유형(수입·지출·적금), 범주, 금액, 모의 가맹점 표기. 각 월에 필수 범주별 집계가 가능하도록 거래를 구성하며, 12개월 중 반복 구독 후보를 검증할 모의 거래를 포함한다. 실제 개인정보나 실제 금융기관 식별자는 포함하지 않는다.

### 분석 데이터

- 거래 기간과 유효 데이터 수
- 범주별 월간 지출 합계
- 반복 지출 후보와 탐지 근거
- 월별 구독·식비 합계와 적금액 집계
- Pearson 상관계수와 계산에 사용된 월별 데이터 수
- 추천 내용과 연결된 근거

### 사건 로그

- 사건 ID, 추적 ID, 장애 주입·탐지·진단·복구·검증 시각
- 장애 신호와 진단 근거
- 복구 제안, 시도 횟수, API 응답 상태
- 사람 승인 또는 에스컬레이션 결과
- 독립 검증 결과와 최종 상태
- 민감정보는 로그에 포함하지 않는다.

로그는 로컬 실습 환경과 EC2의 컨테이너 로그에만 저장하고 개발팀 4명만 접근한다. 데모·교육 검토가 끝나면 로그를 정리하고 EC2 인스턴스를 종료·삭제한다. 알림은 API 응답과 컨테이너 실행 로그에 표시하며 외부 메시징 서비스는 연결하지 않는다.

## 16. 검증 및 완료 기준

### 시나리오

1. 정상 API 응답으로 12개월 분석 결과와 근거가 나온다.
2. HTTP 5xx에서 최대 2회 재시도 후 성공 검증 또는 중단·알림이 수행된다.
3. 지연·타임아웃에서 재시도 상한을 지키고 결과를 기록한다.
4. 지속 연결 실패는 재시도 상한 후 회로 차단 및 사람 알림으로 종료된다.
5. 불완전한 거래 데이터는 정상 분석이나 추천으로 표시되지 않는다.
6. 복구 역할의 자기보고와 독립 검증 결과가 구분된다.
7. EC2 배포본에서 팀 IP로 헬스체크와 정상 분석 요청을 수행하고, 모의 API가 외부에서 차단됨을 확인한다.

### 측정 항목

- 장애 주입부터 탐지까지의 시간(MTTD)
- 장애 주입부터 독립 정상 확인까지의 시간(MTTR)
- 복구 성공률, 오탐률, 평균 재시도 횟수, 에스컬레이션 비율
- 분석 결과에 포함된 월 수와 데이터 근거

완료 판정은 정상 기준 1회에서 오탐이 없고, 세 번의 장애 주입 실행이 3/3 사건으로 기록되며, 재시도 상한 초과가 0건인 것으로 한다. HTTP 5xx와 타임아웃은 재시도 후 검증에 성공하고, 지속 연결 실패는 차단·알림에 성공해야 한다. Pearson 계산은 12개 월별 쌍의 참조 계산값과 비교해 소수 둘째 자리에서 일치해야 한다. MTTD는 3초 이내, 전체 종료는 20초 이내를 목표로 한다. Day 3에는 EC2에서 정상 API 요청과 헬스체크가 성공하고 팀 IP 외의 인바운드 및 모의 API 외부 접근이 차단되어야 한다.

## 17. 3일 MVP 포함·제외 범위

### 포함

- 모의 페르소나의 12개월 거래 내역을 제공하는 모의 API
- 소비 범주·반복 구독 후보 분석과 근거 표시
- 월별 구독·식비 합계와 적금액의 관계 분석
- 통계·규칙 기반 절약 전략 추천
- Python/FastAPI 분석 API와 모의 거래 API를 로컬 Docker Compose에서 검증
- 같은 두 컨테이너를 단일 AWS EC2 테스트 인스턴스에 배포
- 팀 IP 인바운드 제한, 모의 API 내부 네트워크 격리, 헬스체크·정상 API 스모크 확인
- HTTP 5xx, 타임아웃, 연결 실패 장애 시나리오
- 최대 2회 재시도, 차단·중단, 알림, 독립 검증, 사건 기록

### Day별 진행

- Day 1: 서비스 범위와 승인된 PRD 확정

- Day 3: 동일한 컨테이너 구성을 EC2에 배포하고 접근 제한·정상 요청·헬스체크·세 장애 시나리오를 확인한 뒤 임시 리소스 정리

- 결제·취소·이체·투자 등 실행 기능
- 자동 지출 변경, 사용자 대신하는 금융 의사결정
- 전문 재무·투자 자문
- 프런트엔드, 데이터베이스, 사용자 인증, 도메인·TLS, 고가용성·오토스케일링, CI/CD 자동화
