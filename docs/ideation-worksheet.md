# 1. 서비스 선정

## 1.1 어떤 서비스의 장애를 자동 복구할 것인가?

**서비스 이름:** 개인 소비 분석·절약 전략 서비스 (가칭)

**한 문장 설명:**

> 페르소나의 모의 계좌 거래 내역을 분석해 소비 패턴과 반복 지출 후보를 찾고, 근거를 제시하며 절약 전략을 추천한다.

**페르소나:** 수입이 넉넉하지 않은 사회 초년생. 아래 금액은 모두 교육용 모의 값이다: 월 실수령액 2,400,000원, 월세 650,000원, 통신비 55,000원, 복수 구독 합계 약 35,000원, 식비 월 450,000~650,000원, 교통비 약 80,000원, 기타 변동 지출 150,000~350,000원, 적금 월 150,000~350,000원. 실제 개인의 수입·지출이나 현재 시장 가격을 나타내지 않는다.

**정상 실행 흐름:**

```text
사용자
  ↓ 분석 요청
개인 소비 분석 서비스
  ↓ 거래 내역 조회
모의 거래 내역 API (페르소나의 모의 계좌 데이터)
  ↓ 분석 결과
소비 패턴·반복 지출 후보·근거가 포함된 절약 전략 추천
```

**핵심 의존 서비스:**

| 의존 대상 | 용도 | 실패 시 영향 | 모의 구현 여부 |
|---|---|---|---|
| 거래 내역 API | 모의 계좌 거래 내역 제공 | 분석을 시작하지 못하거나 일부 거래를 반영하지 못함 | 모의 API로 제공하기로 함 |
| 분석 기능 | 소비 범주와 반복 지출 후보 분석, 상관 패턴 및 추천 생성 | 결과가 늦거나 불완전할 수 있음 | 통계·규칙 기반으로 수행하기로 함 |

## 1.2 서비스가 멈추면 어떤 영향이 발생하는가?

### 사용자 영향

- 소비 분석과 절약 전략 추천을 받을 수 없거나 늦게 받는다.
- 거래 내역이 누락되거나 불완전하면 추천의 근거와 신뢰도가 낮아질 수 있다.

### 운영 영향

- 장애 원인과 복구 결과를 확인하기 위한 운영자 대응이 필요하다.
- 사람의 실제 금융 의사결정에 영향을 줄 수 있으므로 오류 결과를 정상 결과처럼 표시하지 않아야 한다.

### 데이터·비용·보안 영향

- 실습에서는 페르소나의 모의 계좌 데이터만 사용한다.
- 실제 계좌 연결, 개인정보 처리, 결제 실행, 거래 취소·변경은 범위에서 제외한다.
- 로그는 로컬 실습 환경과 단일 AWS EC2 데모 인스턴스의 컨테이너 로그에만 저장하고 4인 개발팀이 접근한다. 데모·교육 검토 후 로그와 인스턴스를 정리한다.

### 심각도

- [x] 낮음 — 모의 데이터 분석이 지연되거나 실패하지만 실제 금융 거래는 발생하지 않음
- [ ] 중간 — 일부 요청이 실패하고 운영자 대응이 필요함
- [ ] 높음 — 핵심 기능이 중단되거나 데이터·금전 피해 가능

**선택 근거:** 실습 데이터는 모의 값이며 서비스가 추천까지만 제공한다. 잘못된 분석·추천은 사용자가 확인할 수 있도록 근거와 한계를 표시해야 한다.

## 1.3 현재 사람은 장애를 어떻게 발견하고 복구하는가?

| 단계 | 현재 사람의 행동 | 사용하는 정보·도구 | 소요시간 | 문제점 |
|---|---|---|---:|---|
| 탐지 | 요청 실패 또는 응답 지연 확인 | API 상태·요청 시각 | 최대 3초 | 별도 모니터링이 없으면 요청 전까지 감지되지 않음 |
| 진단 | 오류 종류와 로그 확인 | 상태 코드·예외·타임아웃 | 1분 이내 | 증거를 한곳에서 보기 어려울 수 있음 |
| 복구 | API 상태 확인 후 재시도하거나 중단 | 사건 로그·헬스체크 | 최대 20초 | 반복 재시도 제한이 필요함 |
| 검증 | API 재조회와 분석 결과 확인 | 데이터 기간·필드·분석 응답 | 3초 이내 | 실행자 자기보고만으로 완료할 위험 |
| 보고 | 결과와 미해결 사건 기록 | API 응답·컨테이너 로그 | 즉시 | 외부 알림 채널을 사용하지 않음 |

> 이 표는 현재 운영 중인 서비스의 사실 기술이 아니라, 실습에서 비교할 수동 대응 기준이다.

**자동화하려는 단계:** 모의 거래 API 장애의 탐지, 증거 기반 분류, 제한된 복구 시도, 독립 검증 및 결과 기록.

**사람이 계속 담당해야 할 단계:** 절약 추천 검토와 실제 지출·정기 결제에 관한 결정 및 실행.

## 1.4 3일 동안 재현 가능한 최소 서비스는 무엇인가?

### 포함 범위

- 페르소나와 모의 계좌를 위한 모의 거래 내역 사용
- 12개월치 모의 거래 내역을 사용하며 수입, 구독, 식비, 월세, 통신비, 교통비, 기타 변동 지출, 적금 항목을 포함
- 거래 범주별 소비 패턴 분석
- 반복 지출 후보 식별
- 반복 지출 기준: 최근 4개월 중 3개월 이상 같은 가맹점에서 발생하고 각 금액이 해당 기간 중앙값의 ±10% 이내
- 반복 구독은 월 금액과 연간 환산 지출 규모를 근거와 함께 표시하되, 실제 절감액으로 보장하지 않음
- 추천에 사용한 기간·거래·금액 등 근거 제시
- 월별 구독·식비 합계와 적금액 간 Pearson 상관계수 제시. 12개 월별 쌍, 계수(소수 둘째 자리), 기간·표본 수를 표시하고 인과관계로 단정하지 않음
- 분석은 통계·규칙 기반이며, 상관관계만으로 절약 전략을 추천하지 않음. 두 변수 중 하나의 변동이 없거나 12개월 자료가 완전하지 않으면 계수를 표시하지 않고 이유를 알림
- 최근 달 식비가 직전 11개월 중앙값보다 20% 이상 높으면 식비 검토를 제안
- 절약 전략 추천까지만 제공하고 실제 금융 행동은 사용자가 결정
- 모의 거래 API 장애를 안전하게 재현하고 복구 과정을 기록
- API 전용 백엔드로 제공하며 사용자 화면은 만들지 않음
- 로컬 Docker Compose에서 검증한 동일한 두 컨테이너를 단일 AWS EC2 테스트 인스턴스에 배포
- 백엔드 접근은 팀 IP로 제한하고 모의 거래 API 포트는 컨테이너 내부에만 둠

### 제외 범위

- 실제 은행·카드 계좌 연결 또는 실제 개인정보 사용
- 실제 결제, 정기 결제 취소, 이체, 투자 주문 등 금융 행동 실행
- 전문 재무·투자 자문이나 미래 자산의 확정적 예측
- 추천을 근거 없이 자동 생성하거나 상관관계를 인과관계로 표현하는 기능

### 사용할 환경

- [ ] 로컬 프로세스
- [x] Docker Compose — 로컬에서는 분석 API와 모의 거래 API를 별도 컨테이너로 실행하고, AWS에는 같은 구성을 단일 EC2 인스턴스로 배포
- [ ] Kubernetes 로컬 클러스터
- [x] AWS 샌드박스 — 단일 EC2 테스트 인스턴스, 팀 IP에서만 백엔드 API 접근
- [ ] 기타: 개인 노트북

**확정된 기술·팀 제약:** Python, FastAPI, Docker 사용 가능; 개발 인원 4명. 팀 경험 수준은 확인되지 않았으므로 구조를 단순한 결정적 로직으로 제한한다.

### 선택한 장애 유형

- [x] HTTP 5xx — 모의 거래 API 오류 응답
- [x] 타임아웃 — 모의 거래 API 응답 지연
- [x] 의존 서비스 연결 실패 — 모의 거래 API 이용 불가
- [ ] 프로세스 중단 — 이번 MVP 장애 시나리오에서 제외
- [ ] 잘못된 설정 — 이번 MVP 장애 시나리오에서 제외
- [x] 반복 장애 — 재시도 상한 및 회로 차단 검토
- [ ] 기타: 거래 누락·잘못된 필드는 API 장애 복구와 구분해 데이터 품질 문제로 검증 단계에서 보고

# 2. 에이전트 설계

## 2.1 장애를 탐지하는 주체는 누구인가?

**에이전트 이름:** Monitor 역할. MVP에서는 결정적 상태 점검으로 구현한다.

**관찰 데이터:**

- [x] 헬스체크 응답
- [x] 애플리케이션 로그
- [ ] 오류율
- [x] 응답시간
- [ ] 프로세스 상태
- [x] 기타: 거래 API 호출 결과와 요청 식별자

**장애 판정 조건:** HTTP 오류 응답은 즉시 탐지한다. 응답이 3초를 넘으면 타임아웃으로 분류하고, 연결 예외는 연결 실패로 기록한다. 주기적 헬스체크 대신 요청 시점과 복구 전 확인에 사용한다.

**출력 메시지:** 사건 ID, 추적 ID, 장애 유형, 관찰 증거, 발생 시각, 시도 횟수, 제안 행동, 승인 필요 여부, 검증 상태.

## 2.2 원인을 진단하는 주체는 누구인가?

**에이전트 이름:** Diagnosis 역할. 상태 코드·예외·요청 시간에 근거한 결정적 규칙으로 구현한다.

**입력:** 모니터링 증거, 거래 API 응답 상태, 경과 시간, 재시도 이력.

**분류할 장애 유형:**

| 장애 코드 | 설명 | 판단 근거 | 신뢰도 또는 규칙 |
|---|---|---|---|
| API_5XX | 모의 거래 API가 서버 오류 응답 | HTTP 상태 코드와 응답 시각 | 5xx면 장애 |
| API_TIMEOUT | 거래 API가 3초 안에 응답하지 않음 | 요청·타임아웃 시각 | 3초 초과면 타임아웃 |
| API_UNAVAILABLE | 거래 API 연결 실패 또는 헬스체크 실패 | 연결 오류·헬스체크 결과 | 연결 예외면 장애 |

**원인을 판단할 수 없을 때 행동:** 자동 변경 없이 복구를 중단하고 증거와 함께 사람에게 전달한다.

## 2.3 복구를 실행하는 주체는 누구인가?

**에이전트 이름:** Recovery 역할. 허용된 재시도와 중단 상태 흐름으로 구현한다.

**허용된 복구 행동:**

- 일시적인 오류에 대한 제한된 재시도
- API 정상 여부 재확인
- 시도 상한 도달 또는 연속 실패 시 중단 및 에스컬레이션

**금지된 행동:**

- 임의 생성 명령 실행
- 모의 계좌 거래 데이터의 임의 수정·삭제
- 실제 계좌 연결이나 금융 행동 실행
- 복구 검증 전 정상 완료 선언

**필요한 도구·API·명령:** 읽기 전용 모의 거래 API 조회와 헬스체크. 로컬 Docker Compose 및 AWS EC2의 단일 Docker Compose 환경에서 두 API를 실행한다.

## 2.4 복구 성공을 독립적으로 검증하는 주체는 누구인가?

**에이전트 이름:** Verification 역할. Recovery와 분리된 검증 단계로 둔다.

**독립성이 필요한 이유:** 복구를 실행한 주체의 성공 보고만으로 API와 분석 결과가 정상이라고 단정할 수 없기 때문.

**검증 항목:**

- [x] 헬스체크 정상
- [x] 핵심 기능 테스트 통과 여부를 확인할 요구사항
- [ ] 오류율 정상 범위
- [ ] 응답시간 정상 범위
- [x] 데이터 무결성 확인 — 12개월 완전성, 필수 범주·금액 필드 유효성, 거래 ID 중복 여부 확인. ID 중복·누락은 분석 전에 데이터 품질 오류로 보고
- [ ] 회귀 테스트 통과

**복구 실패 판정 조건:** 12개월 자료·필수 범주 누락, 잘못된 금액 형식, 분석 응답 누락, 세 번의 요청 후에도 API 실패 시 미해결로 기록하고 사람에게 전달한다.

## 2.5 오케스트레이터가 필요한가?

- [x] 필요함 — Monitor, Diagnosis, Recovery, Verification 단계 순서와 재시도 상한을 관리할 필요가 있음
- [ ] 필요하지 않음

**판단 근거:** 여러 역할의 순서, 재시도 제한, 실패 시 중단 및 에스컬레이션을 일관되게 관리한다. MVP에서는 역할을 별도 LLM으로 만들지 않고 결정적 로직과 상태 흐름으로 구성한다.

### 오케스트레이터의 책임

- 사건 상태와 처리 순서 관리
- 재시도 상한·타임아웃·회로 차단 적용
- 검증 결과에 따라 완료 또는 에스컬레이션 결정

### 오케스트레이터가 해서는 안 되는 일

- 복구 정책이나 권한 제한 우회
- 거래 내역 또는 금융 행동 직접 변경

## 2.6 에이전트 협업 구조

| 에이전트 | 입력 | 출력 | 호출 주체 | 허용 권한 | 타임아웃 |
|---|---|---|---|---|---:|
| Monitor | 헬스체크·API 호출 결과 | 장애 이벤트와 관찰 증거 | 오케스트레이터 | 조회·사건 기록 | API 요청 제한시간 3초 |
| Diagnosis | 장애 이벤트·증거 | 장애 분류·근거·복구 제안 | 오케스트레이터 | 증거 조회·제안 | 전체 흐름 20초 내 |
| Recovery | 승인된 복구 정책·사건 상태 | 시도 결과 | 오케스트레이터 | 제한된 재시도 | 전체 흐름 20초 내 |
| Verification | 복구 후 API·분석 결과 | 독립 검증 결과 | 오케스트레이터 | 상태·결과 조회 | API 요청 제한시간 3초 |
| Notification | 실패·검증 결과 | 사용자·운영자 알림 | 오케스트레이터 | API 응답·컨테이너 로그 | 전체 흐름 20초 내 |

### 협업 흐름

```text
Monitor가 장애 증거 생성
→ Orchestrator가 사건 생성 및 시도 제한 확인
→ Diagnosis가 장애 유형 분류
→ Recovery가 허용된 제한적 복구 수행
→ Verification이 API와 핵심 분석 결과를 독립 확인
→ 성공이면 종료, 실패·원인 불명·상한 초과면 사람에게 전달
```

# 3. 자율성과 통제

## 3.1 자동으로 실행해도 되는 복구는 무엇인가?

| 복구 행동 | 자동 허용 이유 | 영향 범위 | 선행조건 | 실행 후 검증 |
|---|---|---|---|---|
| 일시적인 API 오류 제한적 재시도 | 모의 데이터 조회에 한정되고 데이터 변경이 없음 | 해당 분석 요청 | 시도 상한·타임아웃 적용 | 재조회 및 결과 확인 |
| 헬스체크 재실행 | 조회만 수행 | 모의 API 상태 확인 | 사건별 호출 제한 | 상태 응답 기록 |

## 3.2 사람의 승인이 필요한 복구는 무엇인가?

| 복구 행동 | 승인 필요 이유 | 승인자 | 승인 타임아웃 | 미승인 시 행동 |
|---|---|---|---|---|
| 데이터나 분석 정책을 변경하는 조치 | MVP에서 변경 기능을 제공하지 않음 | 사용자 | 해당 없음 | 자동 실행 금지·중단·보고 |
| 실제 금융 행동 | 본 프로젝트 범위 밖이며 사용자 결정이 필요함 | 해당 없음 | 해당 없음 | 자동 실행 금지 |

## 3.3 복구를 몇 번까지 재시도할 것인가?

최대 재시도 횟수: 최초 요청 이후 최대 2회 재시도(총 요청 최대 3회). 대기시간은 첫 재시도 전 1초, 두 번째 재시도 전 2초로 한다. 요청 제한시간은 3초이며, 모두 실패하면 중단하고 알림을 보낸다.

대기시간: 1초, 2초. API 요청 제한시간: 3초. 전체 워크플로 타임아웃: 20초.

## 3.4 무한 복구 루프를 어떻게 방지할 것인가?

1. 사건별 시도 횟수와 시각을 기록한다.
2. 최초 요청 뒤 재시도는 최대 2회, API 요청 제한시간은 3초로 제한한다.
3. 전체 처리 제한시간은 20초다.
4. 사건에서 3회 연속 요청이 실패하면 회로를 열고 자동 호출을 중지한다.
5. API 헬스체크가 한 번 정상인 것을 사람이 확인하고 명시적으로 재개하기 전까지 회로를 닫지 않는다.
6. 실패 증거와 시도 이력을 사람에게 전달한다.

## 3.5 잘못된 복구를 어떻게 취소할 것인가?

| 복구 행동 | 변경 전 저장할 상태 | 실패 판정 | 롤백 방법 | 롤백 검증 |
|---|---|---|---|---|
| 읽기 전용 API 재시도 | 변경 없음 | 재시도 상한 초과·검증 실패 | 추가 복구 중단 | 사건 상태와 API 상태 기록 |
| 데이터 변경 조치 | MVP에 변경 기능이 없음 | 해당 없음 | 자동 수행 금지, 사람에게 에스컬레이션 | 해당 없음 |

# 5. 검증

## 5.1 복구 성공을 어떤 지표로 판정할 것인가?

| 지표 | 정상 기준 | 측정 위치 | 실패 기준 |
|---|---|---|---|
| 헬스체크 | 모의 거래 API가 정상 상태 응답 | API 점검 시점 | 제한시간 내 정상 응답이 없음 |
| 오류율 | 장애 주입 3회 중 사건 기록 3회; 정상 기준 요청에서 오탐 0/1회 | 데모 시나리오별 사건 기록 | 장애 누락 또는 정상 요청 경보 |
| 응답시간 | API 요청 3초 이내; 전체 흐름 20초 이내 | 요청·응답 및 최종 상태 시각 | 각각 제한시간 초과 |
| 핵심 기능 테스트 | 모의 거래 내역 분석과 근거 표시 완료 | 복구 후 독립 검증 | 결과 생성 실패·누락 |
| 회귀 테스트 | 장애 복구 후 정상 분석 기준 시나리오 통과 | 독립 검증 단계 | 분석·근거 표시 실패 |
| 상관계수 | 12개월 모의 데이터의 Pearson 계수가 참조 계산값과 소수 둘째 자리까지 일치 | 분석 검증 단계 | 계산 결과 불일치 또는 표본·기간 미표시 |

## 5.2 장애 탐지부터 복구까지 걸린 시간을 어떻게 측정할 것인가?

- 장애 주입 시각: `injected_at`
- 탐지 시각: `detected_at`
- 복구 시도 시각: `recovery_attempted_at`
- 검증 완료 시각: `verified_at`
- 탐지 시간: `detected_at - injected_at`
- 정상화 시간: 성공 검증 시각에서 장애 주입 시각까지
- 목표: 장애 탐지 3초 이내, 정상 결과 또는 실패 알림까지 20초 이내
- 시각 기록 방식과 시간 정밀도: 로컬 시스템 시각, 1초 단위

## 5.3 어떤 로그를 반드시 보존할 것인가?

- 사건 식별자와 요청 추적 식별자
- 장애 주입·탐지·진단·복구 시도·검증 시각
- 장애 신호와 진단 근거
- 복구 전략, 시도 횟수, 결과
- 사람 승인 또는 에스컬레이션 상태
- 독립 검증 결과와 최종 상태
- 민감정보와 실계좌 정보는 기록하지 않음. 실습 데이터는 모의 값만 사용
- 보존 기간 및 로그 접근권한: 로컬 실습 환경과 단일 EC2 데모 인스턴스의 컨테이너 로그에 저장, 4인 팀 접근, 데모·교육 검토 종료 후 삭제

## 5.4 최종 데모에서 어떤 장애를 주입할 것인가?

| 순서 | 장애 | 주입 방법 | 예상 탐지 | 예상 복구 | 성공 증거 |
|---|---|---|---|---|---|
| 1 | 일시적 HTTP 5xx | 첫 호출에서 한 번 오류 후 정상 응답 | 상태 코드 기반 사건 기록 | 재시도 성공·독립 검증 | 3초 이내 탐지, 시도·검증 로그 |
| 2 | 일시적 타임아웃 | 첫 호출에서 한 번 3초 초과 후 정상 응답 | 제한시간 초과 탐지 | 재시도 성공·독립 검증 | 재시도 간격·정상 결과 기록 |
| 3 | 지속 연결 실패 | 세 호출 모두 모의 API 연결 불가 | 연결 오류 기록 | 두 번 재시도 후 회로 차단·알림 | 재시도 상한 준수·사건 종료 기록 |

1. 실제 금융 계좌·개인정보 연동

1. 정상 기준 1회에서 오탐 0건, 장애 주입 시나리오 3개 모두 사건으로 탐지·기록, 재시도 상한 초과 0건을 달성한다.
2. 분석 결과에 사용된 거래 기간·범주·금액 등 근거를 표시하고, 12개월 데이터에서 월별 구독·식비 합계와 적금액의 Pearson 상관 패턴을 인과관계로 단정하지 않고 제시한다.
3. Recovery의 완료 보고와 별개로 독립 검증이 정상 상태를 확인한다.
