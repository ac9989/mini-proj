# Auto Healing 멀티 에이전트 프로젝트 작업목록

## 1. 문서 정보

- 프로젝트명: 개인 소비 분석·절약 전략 서비스 (가칭)
- 기반 PRD: `docs/prd-auto-healing.md`
- PRD 버전: 0.5
- PRD 승인 상태: 승인 (PRD 0.5 승인 기록 및 사용자 확인)

- 상태: 승인 대기

## 2. 프로젝트 목표

3일 프로젝트의 Day 2와 Day 3에 Python/FastAPI 분석 API와 모의 거래 API를 구현하고, 통계·규칙 기반 분석과 안전한 장애 복구 흐름을 로컬 Docker Compose에서 검증한 뒤 동일한 두 컨테이너를 단일 AWS EC2 테스트 인스턴스에 배포한다. 추천은 근거와 한계를 제시하며 실제 금융 행동은 실행하지 않는다.

## 3. 작업 원칙

- 구현 기준은 승인된 PRD 0.5의 FR-001~FR-010, NFR-001~NFR-007이다.
- 4인 팀이 병렬 작업할 수 있도록 API 계약과 사건 필드를 초기에 공유한다.
- 에이전트 역할은 단일 서비스 안의 결정적 로직과 상태 흐름으로 구현한다. 별도 LLM, 프런트엔드, DB, 인증, 도메인·TLS, CI/CD는 추가하지 않는다.
- 거래 자료와 장애 주입은 모의 데이터·모의 API에만 적용한다. 모의 거래 데이터 수정·삭제, 실제 금융 행동, 임의 명령 실행은 금지한다.
- 모든 구현 작업은 테스트·검증 및 완료 증거를 포함한다. 이 문서는 계획이며 작업 생성 시점에 구현·테스트·배포를 완료한 것으로 표시하지 않는다.
- 상태 표기는 `[ ] pending`, `[~] in_progress`, `[x] complete`, `[!] blocked`, `[-] excluded`만 사용한다. 시작 상태는 모두 `[ ] pending`이다.

    - 최근 4개월 중 3개월 이상 같은 가맹점에서 발생하고 각 금액이 해당 기간 중앙값의 ±10% 이내인 구독만 후보로 제시한다.

### 3. 근거 기반 절약 전략 추천

- [ ] 3.1 소비 분석 근거를 연결한 추천 생성
  - 목적: 사용자가 직접 검토할 절약 전략을 관찰 가능한 범주·기간·금액 근거와 함께 반환한다.
  - 관련 요구사항: FR-005, NFR-002, NFR-005
  - 선행조건: 2.1, 2.2
  - 예상 대상 파일:
    - `app/services/recommendations.py`
    - `app/schemas/analysis.py`
    - `tests/unit/test_recommendations.py`
  - 수행 내용:
    - 최근 달 식비가 직전 11개월 중앙값보다 20% 이상 높을 때만 식비 검토를 제안한다.
    - 반복 구독 후보의 월 금액·연간 환산 금액과 가정에 따른 검토 가능 절감액을 표시한다.
    - Pearson 상관계수만으로 추천을 만들지 않고 소비 범주 기준과 반복 구독 근거에 연결한다.
    - 기준에 해당하는 패턴이 없거나 데이터가 부족하면 억지 추천을 만들지 않고 한계를 반환한다.
  - 테스트·검증:
    - 20% 임계 경계, 기준 미달, 자료 부족 입력을 단위 테스트한다.
    - 소비 기준을 충족하지 않고 상관 패턴만 존재하는 입력에서 추천이 생성되지 않는지 확인한다.
    - 모든 추천에 근거 기간·범주·금액이 있는지 확인한다.
  - 완료 기준:
    - 추천은 추정치와 판단 한계를 표시하고 실제 결제 변경·취소 기능을 호출하지 않는다.
  - 완료 증거: 추천 단위 테스트 출력, 분석 API 응답 예시
  - 위험·주의사항: 금융 행동이나 전문 재무 조언처럼 표현하지 않는다.
  - 예상 일정: Day 2

    - 팀 운영자가 승인된 Docker Compose 관리 경로에서 테스트 전용 내부 제어로 5xx·지연 시나리오를 선택한다. 제어 경로를 공개 분석 API에 추가하지 않고 모의 API 포트도 호스트·외부에 공개하지 않는다.
  - 테스트·검증:

    - 동일 장애 시나리오를 반복 수행해 결과가 재현되는지 확인한다.
  - 완료 기준:

  - 위험·주의사항: 실제 외부 서비스나 운영 데이터를 대상으로 장애를 주입하지 않는다.

  - 예상 대상 파일:

  - 위험·주의사항: 실제 외부 서비스나 분석 API를 중단하지 않는다. EC2에서는 7.1에서 확인된 팀 관리 경로와 접근 제한을 사용한다.

    - 정상 분석, 불완전 데이터 거부, 5xx 회복, 타임아웃 회복을 통합 검증한다.
    - 통합 테스트 자동화는 격리된 연결 예외를 사용하고 실제 컨테이너 중단은 4.2의 수동 절차에서만 수행한다.
    - 정상 기준 요청 1회에서 오탐 0건, 장애 실행 3회에서 사건 기록 3건을 확인한다.
    - Pearson 결과를 참조값과 소수 둘째 자리까지 비교한다.
  - 테스트·검증:
    - Docker Compose 로컬 통합 테스트를 실행한다.
    - API별 3초 제한, 전체 흐름 20초, 재시도 최대 2회를 결과와 로그에서 확인한다.
  - 완료 기준:
    - PRD의 로컬 정상·오류 시나리오와 분석 인수조건이 모두 검증된다.
  - 완료 증거: 단위·통합 테스트 결과, API 응답, 시나리오별 사건 로그
  - 위험·주의사항: 테스트 중에도 실제 금융 API나 실제 개인정보를 사용하지 않는다.
  - 예상 일정: Day 2

- [ ] 6.3 성공 지표와 재현 절차 기록
  - 목적: 최종 판정에 필요한 MTTD·MTTR·재시도·오탐 증거를 남긴다.
  - 관련 요구사항: FR-009, NFR-003, NFR-004, NFR-006
  - 선행조건: 6.1, 6.2, 7.3
  - 예상 대상 파일:
    - `docs/demo-evidence.md`
  - 수행 내용:
    - 7.3 동안 접근 가능한 사건 로그의 주입·탐지·검증 시각으로 MTTD와 MTTR을 계산한다.
    - 정상 기준 오탐률, 장애별 복구 성공률·에스컬레이션, 평균 재시도 횟수, EC2 장애 데모 세 건, Pearson 참조값, 분석에 사용한 월 수·데이터 근거를 기록한다.
    - 모의 API 장애 재현·초기화와 로컬·EC2 검증 순서를 간단히 기록한다.
    - 보고서에는 집계 지표·판정 결과만 보존하고 원시 로그·사건 식별자·상세 시각은 7.4에서 제거한다.
  - 테스트·검증:
    - 로그 시각 차이와 계산한 MTTD·MTTR이 일치하는지 확인한다.
    - 제3자가 PRD 범위 안에서 동일 시나리오를 재현할 수 있는지 확인한다.
  - 완료 기준:
    - PRD 완료 기준의 각 판정에 증거 위치와 결과가 연결된다.
  - 완료 증거: 작성된 결과 기록, 로그·테스트 출력 참조
  - 위험·주의사항: 결과 보고는 요구사항 검증 증거에 한정하며 PRD에 없는 기능이나 지표를 만들지 않는다.
  - 예상 일정: Day 3

### 7. EC2 배포·접근 제한·최종 데모·정리

- [ ] 7.1 AWS 배포 사전 조건 확인
  - 목적: 배포 당일 권한·네트워크 준비 미비로 인한 지연을 조기에 발견한다.
  - 관련 요구사항: FR-010, NFR-007
  - 선행조건: PRD Day 1에 확인할 AWS 권한·팀 IP·EC2 관리 경로 준비 사항. Day 2 시작 시 미확인 항목이 있으면 팀·AWS 담당자와 먼저 확인
  - 예상 대상 파일:
    - `docs/demo-evidence.md`
  - 수행 내용:
    - PRD의 Day 1 사전 확인이 완료됐는지 확인한다. EC2 생성 권한, 샌드박스 사용 가능 여부, 팀이 실제 사용할 지정 IP/CIDR, EC2에서 Docker Compose 명령을 실행할 승인된 관리 경로를 확인한다.
    - 권한·팀 IP·관리 경로 중 하나라도 미확정이면 배포를 차단 요인으로 기록하고 AWS 담당자에게 요청한다.
  - 테스트·검증:
    - EC2 생성 권한, 지정 IP, 관리 경로를 담당자에게 확인한다. SSH를 쓰면 관리 포트도 팀 IP로 제한하고 키를 저장소에 넣지 않는다. 리소스 생성 전 승인·비용 조건을 확인한다.
  - 완료 기준:
    - 배포 담당자, 허용 IP 범위, EC2 생성 권한, 원격 Compose 관리 경로가 확인되거나 차단 요인이 명시된다.
  - 완료 증거: 확인 체크리스트와 담당자 확인 기록
  - 위험·주의사항: 구체적인 팀 IP는 문서에 임의로 작성하지 않는다. 권한이 없으면 배포를 시도하지 않는다.
  - 예상 일정: Day 1 사전 확인 완료 여부 확인. 미완료 시 Day 2 초반에 먼저 확인하고 해결 전까지 배포 작업 차단

- [ ] 7.2 단일 EC2에 동일 Compose 구성 배포
  - 목적: 로컬에서 검증한 분석 API와 모의 거래 API를 데모용 EC2에서 실행한다.
  - 관련 요구사항: FR-010, NFR-002, NFR-007
  - 선행조건: 6.2 로컬 통합 검증 통과, 7.1 배포 조건 확인
  - 예상 대상 파일:
    - `compose.yaml`
    - `Dockerfile`
    - `.env.example`
    - `docs/demo-evidence.md`
  - 수행 내용:
    - 단일 EC2 테스트 인스턴스에 Docker Compose로 같은 두 서비스를 배포한다.
    - 분석 API 인바운드는 확인된 팀 IP에만 허용하고 모의 API 포트는 Compose 내부 네트워크에만 둔다.
    - 설정값은 배포 환경에서 주입하고 자격 증명·SSH 키를 저장소에 두지 않는다.
  - 테스트·검증:
    - Compose 서비스 상태와 EC2 헬스체크를 확인한다.
    - 보안 그룹·컨테이너 포트 설정으로 팀 IP 외 분석 API 접근 및 모의 API 외부 접근이 제한되는지 확인한다.
  - 완료 기준:
    - EC2에서 두 컨테이너가 실행되고 비밀값이 저장소에 없으며 접근 범위가 PRD를 따른다.
  - 완료 증거: 배포 상태, 보안 그룹 규칙, 컨테이너 상태 기록
  - 위험·주의사항: 도메인·TLS·인증·CI/CD·HA는 구현하지 않는다. 비용 발생 리소스는 데모 목적과 승인된 샌드박스 범위로 제한한다.
  - 예상 일정: Day 3

- [ ] 7.3 EC2 정상 요청·장애 데모와 원시 증거 수집
  - 목적: 배포 환경에서 정상 동작과 PRD의 장애 복구 완료 기준을 확인한다.
  - 관련 요구사항: FR-008~FR-010, NFR-001, NFR-004, NFR-007
  - 선행조건: 7.2
  - 예상 대상 파일:
    - `EC2 컨테이너 로그(실행 증거)`
  - 수행 내용:
    - 지정된 팀 IP에서 헬스체크와 정상 분석 요청을 실행한다.
    - 승인된 모의 API 시나리오로 HTTP 5xx와 타임아웃을 각 1회 주입한다.
    - 연결 실패 데모에서는 사람이 모의 API 컨테이너만 중단하고 분석 요청의 세 호출 실패와 회로 차단을 확인한 뒤 해당 컨테이너를 다시 실행한다. Recovery가 컨테이너 중단·시작을 실행하지 않는지 확인한다.
    - 모의 API 헬스체크 정상 확인 후 사람이 회로를 명시적으로 재개하고 새 분석 요청을 확인한다.
    - 데모 로그와 사건별 시각은 6.3에서 지표를 계산할 때까지 팀이 접근 가능한 임시 로그로 보존한다.
  - 테스트·검증:
    - 정상 분석 요청과 헬스체크가 성공하며 모의 API는 외부에서 접근할 수 없는지 확인한다.
    - 5xx·타임아웃은 독립 검증 성공, 지속 연결 실패는 재시도 상한·회로 차단·알림에 도달하는지 확인한다.
    - MTTD 3초 이내, 전체 흐름 20초 이내 및 재시도 상한을 기록에서 확인한다.
  - 완료 기준:
    - 세 장애 유형의 EC2 응답·상태 전이와 Recovery 독립 검증 결과가 확인되고, 원시 로그가 6.3 계산 전까지 보존된다.
  - 완료 증거: 헬스체크·분석 응답, 접근 제한 확인, 장애별 사건 로그·시각·상태 전이
  - 위험·주의사항: 배포 장애는 안전 중단하고 로컬 성공으로 EC2 배포 성공을 대신 주장하지 않는다. 서비스 중단·복구는 테스트 중 모의 API 컨테이너에 한해 사람이 수행한다.
  - 예상 일정: Day 3

- [ ] 7.4 교육 검토 후 원시 로그·AWS 자원 정리
  - 목적: 데모·교육 검토가 끝난 뒤 원시 사건 로그와 임시 AWS 자원을 정리한다.
  - 관련 요구사항: NFR-002, NFR-004, NFR-007
  - 선행조건: 6.3 집계 결과 기록, 데모·교육 검토 완료
  - 예상 대상 파일:
    - `docs/demo-evidence.md`
  - 수행 내용:
    - 원시 컨테이너 로그와 사건별 식별자·상세 시각을 정리한다.
    - `docs/demo-evidence.md`에는 개인정보·비밀값·원시 로그 없이 집계 지표, 완료 여부, 자원 삭제 확인만 남긴다.
    - EC2 테스트 인스턴스를 종료·삭제하고, 이 데모를 위해 생성·할당한 EBS 볼륨·스냅샷·공인/탄력적 IP 등 잔존·과금 자원이 있는지 확인해 불필요한 항목을 정리한다. 기존 공용·공유 자원은 삭제하지 않는다.
  - 테스트·검증:
    - EC2 인스턴스·연결 스토리지·공인/탄력적 IP 등 생성한 임시 AWS 자원의 종료·삭제 상태를 확인하고, 원시 로그와 사건별 식별자가 제거됐는지 확인한다.
    - 보고서에 승인된 집계 결과만 남았는지 확인한다.
  - 완료 기준:
    - 교육 검토 후 불필요한 임시 AWS 자원과 원시 사건 로그가 남지 않고 집계 결과만 보존된다.
  - 완료 증거: AWS 종료·삭제 상태, 정리된 로그 상태, 집계 보고서
  - 위험·주의사항: EC2 삭제는 집계 지표를 확인한 뒤, 검토 완료 후에만 수행한다.
  - 예상 일정: 데모·교육 검토 종료 직후. 검토 종료일은 미정이므로 Day 3에 끝난다고 가정하지 않는다.

**복구·배포 흐름:** `5.4 Recovery 구현 → 6.2 로컬 통합 검증 → 7.2 EC2 배포`입니다. 6.2는 5.4를 포함한 전체 로컬 서비스를 검증하고, 7.2는 6.2 통과와 Day 1에 확인하는 7.1(AWS 권한·팀 IP·관리 경로 준비)에 모두 의존합니다.

- 분석·추천 작업(2~3)과 사건 모델·Monitor 작업(5.1~5.2)은 API 계약·스키마 합의 후 병렬 진행할 수 있다.
- 4.1은 1.2 완료 후 분석 기능과 병렬 진행할 수 있다.
- Diagnosis(5.3), Recovery(5.4), Verification(5.5)은 별도 단위 테스트를 두고 Orchestrator의 자기 보고로 검증 결과를 대체하지 않는다.
- EC2 배포(7.2)는 로컬 통합 검증(6.2) 통과 후 시작한다. AWS 권한/IP 준비(7.1)는 PRD대로 Day 1에 확인하며, 미완료일 때만 Day 2 초반에 보완 확인한다.
- 순환 의존성은 없다. 실제 앱 경로는 현재 저장소에 없으므로 작업 시작 시 폴더 구조를 위 경로에 맞춰 생성한다.

## 8. Day 2 계획

**목표: 로컬 Docker Compose에서 정상 분석과 세 장애 흐름을 검증할 수 있는 상태.** 4인 병렬 작업을 위해 API·사건 스키마를 먼저 합의하고, AWS 권한·팀 IP 준비도 이른 시간에 확인한다.

- 1.1~1.3: 두 API, 모의 거래 데이터, 요청 유효성 검사
- 2.1~2.2 및 3.1: 분석·상관계수·추천 근거 구현
- 4.1~4.2, 5.1~5.6: 장애 재현·복구 절차, 사건 모델, 감지·진단·복구·독립 검증·오케스트레이션 흐름
- 6.1~6.2: 로그·단위 테스트·Compose 통합 테스트
- 7.1: PRD Day 1에 확인하기로 한 AWS 권한·팀 지정 IP·원격 Compose 관리 경로가 준비됐는지 확인. 미완료 상태면 Day 2 시작 즉시 확인하고 해결 전까지 EC2 배포 차단
- 종료 기준: 정상 기준 요청, 12개월 분석, 데이터 오류 차단, 3개 장애 시나리오가 로컬에서 기록·검증됨

## 9. Day 3 계획

**목표: 검증된 구성을 EC2에 배포해 접근 제한과 최종 완료 기준을 확인한다. 자원 정리는 데모·교육 검토가 실제로 끝난 뒤 수행한다.**

- 7.2: 단일 EC2에 두 컨테이너 배포, 팀 IP 제한, 모의 API 내부 격리 확인
- 7.3: 정상 요청·헬스체크와 3개 장애 데모, 독립 검증 및 회로 차단 확인
- 6.3: 데모 로그로 재현 절차와 MTTD·MTTR·장애 판정 결과를 집계해 기록
- 7.4: 데모·교육 검토가 끝난 직후 집계 기록을 보존하고 원시 로그·AWS 임시 자원을 정리한다. 검토가 Day 3 이후라면 정리 완료를 Day 3 종료 기준으로 표시하지 않고 후속 일정과 비용 책임자를 기록한다.
- 종료 기준: EC2 배포 증거 확보와 집계 지표 확인. 로그·AWS 임시 자원 정리는 데모·교육 검토 종료 후 별도 확인한다.

## 10. 위험과 차단요인

| 위험·차단요인 | 영향 | 대응 |
|---|---|---|
| AWS 생성 권한 또는 지정 팀 IP가 준비되지 않음 | Day 3 배포 불가 | PRD 일정대로 Day 1에 준비됐는지 확인한다. 빠진 항목은 Day 2 시작 즉시 확인하고, AWS 담당자 확인 전 리소스를 만들지 않는다. |
| 원격 Compose 관리 경로가 준비되지 않음 | EC2에서 안전한 장애 주입·복구 및 리소스 정리 불가 | 7.1에서 팀 IP 제한이 적용된 승인 경로를 확인한다. mock API 포트를 외부에 공개해 대체하지 않는다. |
| Day 2에 분석·복구·테스트가 몰림 | 로컬 통합 검증 지연, Day 3에 미검증 코드 배포 위험 | API·사건 계약을 먼저 고정하고 4인 병렬 진행. Day 2 종료까지 6.2 통과가 안 되면 검증되지 않은 구성을 EC2에 올리지 말고 일정 위험을 보고한다. |
| 에이전트 역할을 별도 LLM·서비스로 과도하게 분리 | 구현·통합 부담 증가 | PRD대로 한 FastAPI 앱 안의 결정적 역할 함수와 단일 오케스트레이터로 구성한다. |
| 모의 데이터가 의도한 반복·상관 패턴을 보여주지 않음 | 분석 수용 기준 검증 실패 | 사전에 정한 고정 모의 입력과 참조 계산값을 함께 관리하고 실제 금융자료는 사용하지 않는다. |
| AWS 테스트 자원이 데모·교육 검토 뒤 남음 | 불필요한 비용 | 7.4에서 검토·집계 결과 확인 후 EC2와 생성한 스토리지·공인 IP 등 임시 자원, 원시 로그의 정리 상태를 확인한다. 검토가 지연되면 자원 소유자와 비용 부담 기간을 명시한다. |

**일정 적합성 판정: 일부 축소 필요.** 4인 팀이라도 개발·검증 가능한 날은 사실상 Day 2이며 Day 3에는 배포·데모가 예정되어 있어 일정 여유가 작다. 축소안은 분석 기능이나 장애 시나리오를 빼는 것이 아니라, 각 에이전트를 별도 서비스·프로세스로 만들지 않고 한 FastAPI 앱 안의 결정적 역할 함수와 단일 오케스트레이터로 통합하는 것이다. 이는 PRD의 결정적 로직 구성과 일치한다. 추가 범위인 UI·DB·별도 LLM·CI/CD·중복 결제 탐지는 포함하지 않으며, 승인된 PRD 요구사항은 임의로 제거하지 않는다. Day 2 로컬 통합이 실패하면 미검증 기능을 성공으로 처리하지 말고, PRD 범위 축소 또는 일정 변경을 다시 승인받는다.
